# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Solution Overview

`SpeiseDirekt3.sln` contains five .NET 9 projects:

| Project | Type | Purpose |
|---|---|---|
| `SpeiseDirekt3/` | Blazor Server web app | Restaurant back office (menus, categories, items, allergens, combos, QR codes, analytics, user management), public menu display and the landing page on `/` |
| `SpeiseDirekt.Api/` | ASP.NET Core Web API | REST API (Swagger, Identity API endpoints) over the same data |
| `SpeiseDirekt.Model/` | Class library (root namespace `SpeiseDirekt`) | Shared core: entities, DbContext, migrations, repositories, services, authorization, DI setup |
| `SpeiseDirekt.Api.IntegrationTests/` | xUnit test project | Integration tests for every API controller |
| `SpeiseDirekt3.E2ETests/` | xUnit + Playwright test project | Browser end-to-end tests for the Blazor app (public pages, QR resolution, auth, back office) |

Both `SpeiseDirekt3` and `SpeiseDirekt.Api` reference `SpeiseDirekt.Model` and share one SQL Server database (connection string `server`).

## Development Commands

Run from the repository root.

### Building and Running
- **Build everything**: `dotnet build`
- **Run Blazor app**: `dotnet run --project SpeiseDirekt3` (https://localhost:7051, http://localhost:5010)
- **Run Web API**: `dotnet run --project SpeiseDirekt.Api` (https://localhost:7254, http://localhost:5289; Swagger UI at `/swagger` in Development)
- **Watch mode**: `dotnet watch run --project SpeiseDirekt3`
- **Run Blazor app without SQL Server**: set `ASPNETCORE_ENVIRONMENT=E2E` (`Program.E2EEnvironment`): SQLite (connection string `e2e`, default `speisedirekt-e2e.db`), schema via `EnsureCreated()` (`E2EDatabaseInitializer`, no migrations), static web assets enabled. The database starts empty.
- **Preview environment** (`ASPNETCORE_ENVIRONMENT=Preview`, `Program.PreviewEnvironment`; the PR preview on server2 runs with it): production code paths plus `appsettings.Preview.json`. `Preview/PreviewSeedHostedService` runs `PreviewSeeder` at every start, i.e. right after the CI job copied the production database and applied the PR's migrations: for the user in `PreviewSeed:Email` (a sub-account seeds its owner's tenant) it adds three demo menus (`Preview: Gasthaus Zur Post` Classic with four categories (three with a subtitle), 13 items, six allergens, a combo, item labels, price variants on the drinks and extras on two dishes; `Preview: Mittagskarte` Modern; `Preview: Bar & Lounge` Dark), five QR codes (`Preview: Tisch 1`, `Preview: Mittag`, `Preview: Bar` direct; `Preview: Eingang (Zeitplan)` time table; `Preview: Tagesaktion (Kalender)` calendar) and, only when the tenant has none, a restaurant profile "Gasthaus Zur Post" (links to `https://example.com`). Idempotent by name: a menu or QR code that already exists in the tenant is left alone (not enriched either), an existing profile is never touched. Unknown e-mail = nothing happens, a failure is logged and the app starts anyway, `PreviewSeed:Enabled=false` switches it off. The CI step "Preview-Seed prüfen" prints the journal line.
- **Manual API requests**: `SpeiseDirekt.Api/SpeiseDirekt.Api.http`

### Testing
- **Run all tests**: `dotnet test`
- **Run a single test class**: `dotnet test --filter "FullyQualifiedName~MenusControllerTests"`
- **Run a single test**: `dotnet test --filter "FullyQualifiedName~MenusControllerTests.GetAll_ReturnsSeededMenus"`
- **Run only the E2E tests**: `dotnet test SpeiseDirekt3.E2ETests` (no SQL Server needed; Chromium is installed by Playwright on first run, or set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` to an existing binary)

### Database Operations
Migrations live in `SpeiseDirekt.Model/Data/Migrations`, so the EF commands need both project flags:
- **Create migration**: `dotnet ef migrations add <MigrationName> --project SpeiseDirekt.Model --startup-project SpeiseDirekt3`
- **Update database**: `dotnet ef database update --project SpeiseDirekt.Model --startup-project SpeiseDirekt3`
- **Remove last migration**: `dotnet ef migrations remove --project SpeiseDirekt.Model --startup-project SpeiseDirekt3`

### Deployment
CI/CD since 2026-10-31 (`.github/workflows/`), running on the self-hosted ARM64 runner of the CI host (`actions-runner-speisedirekt`) and deploying to server2 via SSH/rsync. No Docker. Only the Blazor app `SpeiseDirekt3` is deployed; the Web API is not hosted anywhere.
- **`deploy.yml`** — on every push to `master`: restore, build, `dotnet test` (a red test stops the deployment), `dotnet publish` of the Blazor app (portable, framework-dependent — server2 runs it with `dotnet SpeiseDirekt3.dll`), EF migrations bundle for linux-x64, rsync to `server2:/var/www/SpeiseDirekt.next`, **COPY_ONLY backup of the `speisedirekt` database** to `/var/opt/mssql/backup/deploy` (the last ten are kept), bundle against the connection string from `Speisedirekt.service`, directory swap, restart, smoke test of https://app.speisedirekt.de.
- **`ci.yml`** — PR preview at https://preview.speisedirekt.de: every open PR against `master` is deployed when opened and on every push (no label needed). One slot — the most recently pushed PR wins. Build of the merge commit (master + PR), tests, copy of the production database to `speisedirekt-pr-preview` (`deploy/preview/db-kopie.sql`, run with `sa` from the CI host), migrations against the copy, `speisedirekt-preview.service` (user `sdpreview`, port 5013) on server2, comment in the PR with the applied migrations. `workflow_dispatch` with a PR number redeploys a preview by hand.
- **`pr-preview-abbau.yml`** — stops the preview when its PR is closed; the database copy stays until the next run.
- `.config/dotnet-tools.json` pins `dotnet-ef` for the bundle (`dotnet tool restore`). Host-side prerequisites (runner, secrets, unit files, Apache vhosts, SQL login) are documented in the CI host's `CLAUDE.md`.
- `SpeiseDirekt3/SendToProd.ps1` (manual publish + `scp`) is superseded by the pipeline; the file is not tracked in the repository.

## Architecture

### Technology Stack
- **Framework**: ASP.NET Core 9.0 (Blazor Server: the back office is Interactive Server, the guest pages and the landing page are static SSR; Web API with controllers)
- **Database**: SQL Server via Entity Framework Core 9 (split queries enabled)
- **Authentication**: ASP.NET Core Identity. Cookies in the Blazor app; `AddIdentityApiEndpoints` / `MapIdentityApi` in the API
- **UI**: back office: Tailwind CSS via the Play CDN `cdn.tailwindcss.com` (config inline in `SpeiseDirekt3/Components/App.razor`: the palettes `brand` (alias `primary`) and `accent` map to the variables of `css/brand.css`) — the **only** remaining external asset, and never loaded on the guest pages or the landing page (they have their own CSS/JS, see *Guest pages* and *Landing page*). Everything else is in the repo: Bootstrap 5.3.3 (`wwwroot/lib/bootstrap`), Chart.js 4.6.1 + chartjs-adapter-date-fns 3.0.0 (`wwwroot/lib/chartjs`, analytics page), FullCalendar 6.1.22 standard bundle (MIT, `wwwroot/lib/fullcalendar` with LICENSE and a README: tarball URL, `dist.integrity`, how it was verified, why not 7.x; byte-identical to the tarball via `.gitattributes`; loaded lazily by the calendar wrapper only, never on guest pages), fonts (`wwwroot/fonts`, `css/fonts.css`: Inter, Manrope and the theme fonts, woff2, latin + latin-ext, SIL OFL licenses in `fonts/licenses`). Icons are inline SVGs (no icon font).
- **AI**: Microsoft.Extensions.AI with Ollama (`llama3.2:latest` at `http://localhost:11434`, hard-coded in `SpeiseDirekt3/Program.cs`)
- **Images**: SixLabors.ImageSharp for resizing; images are stored as bytes in the database (`Image` entity)
- **QR codes**: QRCoder (PNG generated in `SpeiseDirekt3/Controller/ImageController.cs`)
- **Tests**: xUnit, FluentAssertions, `WebApplicationFactory`, SQLite (in-memory for API tests, temp file for E2E), Microsoft.Playwright
- **Localization** (AP12): ASP.NET Core localization with `.resx` (English neutral, German `.de`), chosen only by the browser's `Accept-Language` — back office, account pages and landing page; the guest pages keep the menu's language. See *Localization* below.

### SpeiseDirekt.Model (shared core)
- `Model/Model/`: one file per entity
  - `Menu` (`Description` optional since AP13 — it was `[Required]` while the settings form showed no message, so clearing it silently blocked saving; never null, empty = no intro line on the guest pages; with `DesignTheme`: Elegant, Modern, Classic, Minimal, Fancy, Dark — styles the guest view, see below; `MenuLanguage` (21 values); and `TranslationGroupId` (`Guid?`, migration `AddMenuTranslationGroup`): menus with the same group id are **language versions** of each other, at most one per language — filtered unique index `(TranslationGroupId, Language)` where the id is not null, on SQL Server and SQLite; managed only by `IMenuTranslationService`) → `Category` (optional subtitle `Description`, ≤ 200) → `MenuItem` (labels `IsVegan`, `IsVegetarian`, `IsSpicy`, `IsHalal`, `IsAlcoholFree`, `IsNew`, `IsPopular`; `Description` is optional). `Category` and `MenuItem` carry `SortOrder` (migration `AddCategoryAndMenuItemSortOrder`, default 0): every list, the guest display and the API order by `SortOrder` then name through `Infrastructure/DisplayOrder.cs`; new entries get last + 1 within their parent, the back office reorders by drag handle (`Shared/Sortable/SortableList`, AP11).
  - `MenuItemPriceOption` (migration `AddRestaurantProfileLabelsAndPriceOptions`, cascade with its item): `Kind` `Variant` (alternative size/version with its own price, e.g. "0,25 l" / "0,5 l") or `Extra` (optional add-on, e.g. "+ Halloumi"; JSON `"Variant"`/`"Extra"`), `Name` ≤ 60, `Price` ≥ 0, `SortOrder` within its kind. **Rule:** an item with at least one variant has `Price` = the lowest variant price (`Infrastructure/PriceOptions.ApplyLowestVariantPrice`, applied by the item editor, the API and the seeders), so ordering, combos and old clients keep a meaningful price; guests read it as "from € x".
  - `RestaurantProfile` (one per tenant, unique `ApplicationUserId`): `Name` (required), `Description` ≤ 1000, `LogoImagePath`/`CoverImagePath` (stored like `MenuItem.ImagePath`, `image/{id}`), `Phone`, `Email`, `Website`, `InstagramUrl`, `FacebookUrl`, `GoogleReviewUrl` (absolute http/https, `[HttpUrl]`/`[OptionalEmail]` in `ValidationAttributes.cs`, empty allowed), `Address` and `OpeningHours` (multi-line free text). Stored trimmed, empty → null, line breaks `\n`.
  - `Allergen`: belongs to a menu (`MenuId`, short `Code` + `Name`); many-to-many with `MenuItem` via join table `MenuItemAllergen`
  - `MenuCombo` / `MenuComboItem`: combo offers per menu, triggered by a `TriggerMenuItem`, with a `ComboPrice` and a list of included items
  - `QRCode`: points to a menu directly, or is time-table based (`TimeTableEntry`) or calendar based (`CalendarEntry`). `IValidatableObject` checks for overlapping time windows and date ranges.
  - `TenantSubscription`: paid vs. free tier, `MaxUsers`, `PlanName`
  - `Image` (immutable bytes; **may be referenced by several items** — a language copy points to the original's photos — so never delete an `Image` when an item or menu is deleted without checking references; today nothing does, replacing a photo uploads a new one), `TranslationCache`
  - Analytics: `MenuView`, `MenuItemClick` (not tenant-scoped, FKs with `NoAction`)
- `Model/PermissionModels.cs`: `TenantRole` (AP14: `Owner` = 0, `Manager` = 1), `[Flags] Permission` enum, `TenantUser` (a team member of a tenant, always a manager; its `Permissions` column is no longer read and always 0)
- `Model/Dto/`: shared DTOs (`CreateMenuItemDto`, `BreadcrumbItem`)
- `Data/ApplicationDbContext.cs`: Identity DbContext, global query filters, relationship config, automatic `ApplicationUserId` assignment
- `Data/ApplicationUser.cs`: Identity user with `TenantOwnerId` (null = tenant owner, set = sub-account)
- `Infrastructure/ServiceExtensions.cs`: `ConfigureServices()` registers the shared services and repositories (DbContext-dependent ones as `Transient`). Both hosts call it.
- `Infrastructure/`: authorization (see below), `TenantClaimsTransformation`, `CalendarSchedule` (**the one place for the calendar rules** of a calendar-based QR code: `IsActiveOn(entry, date)`, `ActiveEntry(entries, date)` — one-off (date or period) before weekly, then the earliest `Date`, input order on a tie —, `Collide(a, b)` — only entries of the same kind: two periods sharing a day, two weekly entries on the same weekday with overlapping periods —, `Conflicts`, `HasEndBeforeStart`; used by `MenuService`, `QRCode.Validate` and the back-office calendar), `EditFormExtensions`, `DisplayOrder` (ordering helpers), `ItemLabels` (**the one list of item labels**: stable `Key`, property, German and English guest text (`GuestTextFor(german)`), `Dietary`/`Highlight`, display order; `ActiveFor(item)` applies "vegan hides vegetarian", `Matches` lets a vegan item count as vegetarian in filters; editor, item table, guest view and guest filter all read it), `PriceOptions` (`Variants()`/`Extras()` in display order, `HasVariants`, `ApplyLowestVariantPrice`, `Renumber`), `GuestMenuQueries.IncludeGuestContent()` (categories → items → allergens and price options in order, for guest pages), `ImagePaths` (`image/{id}` ↔ id, API URL `/api/images/{id}`), `MenuLanguages` (**the one table of menu languages**: per `MenuLanguage` the ISO code for `lang`/`hreflang`, the endonym ("Deutsch", "Français", "日本語"), English and German name, `og:locale`; `InLanguageOrder`), `EuAllergens` (the 14 EU allergens A–R with German/English names; `NameIn(language, code, name)` renames a standard name for a copy)
- `Repository/`: repositories for Menu, Category, MenuItem, QrCode, Image and MenuCombo (used by the API)
- `ServiceInterface/` and `ServiceImplementation/`: services (see below)

### Multi-Tenant Architecture
- A **tenant** is the owner account. Sub-accounts = team members (`ApplicationUser.TenantOwnerId` set, plus a `TenantUser` row: display name, active or not; always a manager) work on the owner's data.
- Tenant-owned entities implement `IAppUserEntity` (`ApplicationUserId` = tenant owner ID).
- `ApplicationDbContext.OnModelCreating` applies global query filters on `ApplicationUserId` for MenuItem, Category, Menu, QRCode, TimeTableEntry, CalendarEntry, Allergen, MenuCombo, MenuComboItem, MenuItemPriceOption and RestaurantProfile.
- `ChangeTracker` events set `ApplicationUserId` on Added/Modified entities from `IUserIdProvider`. Adding, modifying or deleting an `IAppUserEntity` **throws** if no authenticated user is present; merely tracking queried entities (anonymous public pages) is allowed.
- `TenantClaimsTransformation` adds `TenantOwnerId` and `TenantRole` claims for sub-accounts.
- `IUserIdProvider.GetUserId()` returns the **tenant owner ID** (the `TenantOwnerId` claim for sub-accounts, otherwise `NameIdentifier`) and is what the query filters use. `GetActualUserId()` returns the logged-in user. Both return `Guid.Empty` when unauthenticated.
- Public/anonymous paths (QR code resolution, public menu display) use `IgnoreQueryFilters()`. See `MenuService`, `MenuDisplayPage.razor`, `QrRedirect.razor`. The owner preview `/menu/preview/{id}` (`MenuPreviewPage.razor`) is `[Authorize]` and uses the query filters (own tenant only); it renders with `TrackClicks = false` so item clicks are not counted in the analytics.

### Authorization
- **Roles** (AP14, operator decision 19.11.2026: "only two roles"): the **owner** (the account that registered: no `TenantOwnerId`, no `TenantUser` row, exactly one per tenant, every permission; not invited, edited or removed on the team pages) and **managers** (every invited member: menus with their language versions, categories, items, allergens, combos, QR codes incl. download, the restaurant profile — all four of view/create/edit/delete — and analytics; **not** the team). Nothing else: no per-member permission matrix, no other roles (general manager, cashier, employee and driver are gone, so are the areas delivery and subscription). The data-only migration `TeamRolesOwnerAndManager` (`UPDATE [TenantUsers] SET [Role] = 1, [Permissions] = 0;`, `Down` a documented no-op) made every existing member a manager.
- **Permissions**: `Permission` is a `[Flags] long` enum (`MenusView`, `MenusCreate`, …, `UsersDelete`). When adding a value, pick an unused bit; the bits are not in order, and 30, 32 and 33 (the former `SubscriptionManage`, `DeliveryView`, `DeliveryManage`) stay unused.
- **Policies**: `AuthorizationOptions.AddPermissionPolicies()` generates one policy per permission, named `Can{Action}{Area}` (e.g. `MenusView` → `CanViewMenus`). `PolicyNames` holds constants for them; they must match `GetPolicyName` (e.g. `CanViewMenuCombos`).
- **Resolution** (`PermissionService`, from the database, not from claims): an account without `TenantOwnerId` is the `Owner`, an account with an **active** `TenantUser` row a `Manager` (the row's `Role` and `Permissions` are not read), anything else — an inactive member, a missing row, an account that no longer exists — has no role and no permission, at once. `PermissionDefaults.For(role)` holds the two sets (`Owner` = every defined bit, `Manager` = everything but `Users*`).
- **API**: controllers use `[Authorize(Policy = PolicyNames.Can…)]` per action. `ImageUploadController` and `MenuDisplayController` have no permission policies.
- **Blazor**: pages use `@attribute [Authorize]` and check `IPermissionService.HasPermissionAsync(Permission.…)` to show/hide actions. **Every area page checks its view permission first** (`Shared/PageAccess.RequireAsync(permission, navigation)`: without it a full load of `/Account/AccessDenied`, the behaviour `/qrcodes` always had): dashboard, menus, menu overview and preview (`MenusView`), categories, items list and item page, allergens, combos, QR codes, restaurant (`MenusView`) and the team pages (`UsersView`/`UsersCreate`/`UsersEdit` — the owner's); the menu settings and the QR editor send a user without the edit right to their list, which then denies; analytics without `AnalyticsView` goes to the dashboard. So a manager is denied only the team, and an inactive or removed member every page of the tenant (AP14; before, such a member could read the menus). The navigation lists only what the account may open (`ShellNavItem.Requires`, `ShellNavigation.VisibleFor`): a manager has no "Team", the dashboard no team tile. **Read-only branches no role reaches any more** (kept, they need a view right without the edit right): the QR editor's read-only mode (`/qrcode/edit/{id}` with `QrCodesView` but no `QrCodesEdit`: notice, disabled fields, the calendar without panel or dragging, "View" on `/qrcodes`), the item page's (`item-read-only`), the restaurant profile's (`profile-read-only`), the lists without create/edit/delete buttons and `SortableList` without `OnMove` (no handles).
- **PaidTenant** policy (`PaidTenantHandler`): passes for tenants with an active paid `TenantSubscription`; free tenants pass while they have fewer than 100 QR codes. `/qrcodes` disables the "Create New QR Code" button, and `/qrcode/edit` checks it as well (on load for a new code and again on save; editing existing codes stays allowed).
- **User limit**: creating a team member fails once the active `TenantUser` count reaches `TenantSubscription.MaxUsers` (no subscription row = no limit; activating a member again does not check it).

### Key Services
- **IMenuService**: resolves the active menu for a QR code. Precedence: matching calendar entry for today (if `IsCalendarBased`, `CalendarSchedule.ActiveEntry`), then the active time-table window (if `IsTimeTableBased`, also across midnight; no active window = null), otherwise the direct menu. Uses the injected `TimeProvider` (`GetLocalNow()`), registered as `TimeProvider.System` in `ServiceExtensions`.
- **IPermissionService**: current role (`Owner`, `Manager` or null) and permissions, resolved from the database once per instance (the service is transient: every component gets its own)
- **ITrackingService** / **IAnalyticsService**: records menu views and item clicks (session cookie `SpeiseDirekt_SessionId`) and aggregates them for the analytics page and API.
- **IImageUploadService**: `ImageDatabaseUploadService` (registered in the Blazor app) stores images in the DB and returns `image/{id}`; `DeleteImageAsync` takes that path (or the bare id). `ImageUploadService` (file-based, `wwwroot/uploads/`) still exists but is not registered.
- **IRestaurantProfileService**: `GetForOwnerAsync(ownerId)` / `GetForMenuAsync(menuId)` for anonymous guest pages (`IgnoreQueryFilters`, `AsNoTracking`, null when none; owner = `Menu.ApplicationUserId`; `GuestMenuLoader.BuildAsync` calls `GetForOwnerAsync` once per request, also in the preview), `GetOwnAsync()` and `SaveOwnAsync(values)` (create or update, normalizes and validates, returns whether it was created) for the back office and the API.
- **IMenuTranslationService** (`MenuTranslationService`, back office + API, tenant query filters): `GetVersionsAsync` (the group in language order, the menu included), `GetLinkCandidatesAsync` (menus in a free language that are not linked elsewhere), `CreateTranslationAsync(menuId, language)` ("Add translation": copies name → "X (English)" (unique, a language suffix is replaced, then " 2", …), description, theme, categories, items with every field/label/sort order/price option/photo reference/allergen link, the menu's allergens (EU standard names in the target language, own names unchanged) and combos into new rows, links both menus; one `SaveChanges`; no QR code), `LinkAsync`, `UnlinkAsync` (a group left with one menu is dissolved), `ValidateLanguageAsync` (message when another version has the language). `LeaveGroupOnDeleteAsync` is called by both menu deletes (back office, API): the others stay linked, a single one left is unlinked. No machine translation (owners translate the copy by hand).
- **IImageResizeService**: resizes uploads (ImageSharp)
- **IMenuItemGenerator**: AI-generated menu items via Ollama (Blazor app only)
- **IAutomaticTranslator** / **ITranslationApiService**: Azure Translator with DB cache (`TranslationCache`), incl. allergen names. Implemented but not registered or used (operator decision: key and cost; language versions are translated by hand).
- **INotificationService**: in-app notifications

### Localization: English and German (AP12)

The back office (incl. the account pages under `/Account`) and the landing page speak **German or English**; the guest pages keep their own mechanism (the menu's language, `GuestText`). AP12a (foundation, shell, account pages, dashboard, landing page) and AP12b (every area page, the model's messages, FullCalendar, Chart.js) are done — see *Open points* below.

- **Only the browser decides**, through `Accept-Language` — no switcher, no cookie, no query string (`Localization/AppCultures.Select`, the one provider `BrowserLanguageCultureProvider`; `LocalizationSetup.AddAppLocalization`/`UseAppRequestLocalization` in `Program.cs`). Entries by quality, the first German or English one wins; regional variants count (`de-AT` → de, `en-GB` → en); `*` → German; `q=0` is skipped. **No header** (crawlers, curl) or an unreadable one → **German**; a header **without a supported language** (only `fr`) → **English**. Cultures are the neutral `de`/`en` (`CurrentCulture` = `CurrentUICulture`; formats like de-DE / en-US).
- **Interactive Server**: the circuit takes the culture of the `/_blazor` request (it carries the same `Accept-Language`) and keeps it across client-side navigations; texts made in the circuit at event time (announcements, confirmations) are in that language.
- **Documents**: `<html lang>` of the back-office, landing and account (`[AuthPage]`) documents is `AppCultures.HtmlLang`; component pages other than the guest pages send `Vary: Accept-Language` and `Content-Language` (Blazor's SSR responses already send `Cache-Control: no-cache, no-store`; `private` is set when nothing else did). The landing page has `og:locale` `de_DE`/`en_US` and its language's `og-<lang>.png`; **one URL serves both languages**, so the canonical stays that URL and there is **no `hreflang`**. Its section anchors stay German (`#funktionen`, `#so-funktionierts`) in both languages.
- **Guest pages** (`[GuestPage]`: `/qr`, `/menu`, `/menu/preview`) are excluded from request localization and **pinned to the invariant culture** (endpoint metadata, `LocalizationSetup.IsGuestPage`): nothing on them follows the browser; `GuestText` formats prices with its own number format; no `Vary`. The editor's preview iframe is a guest page too.

- **Today**: `CommonText` (buttons and words every area uses: Save, Cancel, Delete, Edit, Add, Remove, Close, Back, OK, Optional, Done, Loading…, Saving…, Preview, `PageTitle` = "{0} - Speise-Direkt", the role names `Role_<TenantRole>` = `Role_Owner`/`Role_Manager`, German "Besitzer"/"Manager"), `ShellText` (chrome, context bar, sortable handles and announcements, `MultiSelectComboBox`, pagination, info popover, `/Error`), `AccountText` (every `/Account` page, their validation and status messages), `IdentityText` (Identity's errors, `Account/LocalizedIdentityErrorDescriber`, registered with `AddErrorDescriber`), `DashboardText`, `LandingText`, and one per area page (AP12b): `MenusText` (list, overview, settings, language versions, design names `Theme_<DesignTheme>`), `CategoriesText`, `ItemsText` (items list and item page, label names `Label_<property without Is>`), `AllergensText`, `CombosText`, `QrCodesText` (list, editor, time table, calendar editor), `AnalyticsText` (page and the Chart.js texts), `RestaurantText`, `TeamText` (team pages, the roles sentence `RolesNote`); `ShellText` also holds the FullCalendar wrapper's texts (`Calendar_*`). In `SpeiseDirekt.Model/Resources`: `ValidationText` (generic DataAnnotations messages with `{0}` = the field: `Required`, `MaxLength`, `LengthRange`, `Range`, `EmailAddress`, `Url`, `Phone`, `Compare`, `Number`, `PriceFormat`) and `ModelText` (full-sentence messages of the entities' attributes, `HttpUrl`/`OptionalEmail`, `QRCode.Validate` and `MenuTranslationService`) — the Model's texts are read through the generated class (`SpeiseDirekt.ValidationText.Required`), not `IStringLocalizer` (the Model's root namespace differs from its assembly name).
- **One resource per area**: a new page goes into its area's resource, a new area gets its own (`<Area>Text.resx` + `.de.resx`; the class appears with the next build). Model messages: `ModelText`, read through the generated class and formatted with `string.Format(CultureInfo.CurrentCulture, …)`.
- **Helpers**: `UiMarkup.Strong(T["Key"], name)` — a sentence whose `{n}` arguments are shown in `<strong>` ("The sections of **Lunch**."), sentence and arguments HTML-encoded; `MenuDisplay.ThemeName`/`LanguageName` and `MenuLanguageInfo.DisplayName` (German or English language name by `CurrentUICulture`); `ItemsDisplay.LabelName`. Optional fields: `C["OptionalSuffix"]` = "(optional)".
- **In components**: `@inject IStringLocalizer<DashboardText> T` (the area) and `@inject IStringLocalizer<CommonText> C` (common words) — explicit per file; `@T["Key"]`, `@T["Key", arg0, arg1]`. Keys are **stable names**, PascalCase segments joined by `_` (`Login_Heading`, `Stat_ItemsInTotal`, `Valid_EmailRequired`, `Status_PasswordChanged`), never the English sentence. A key kept in data (navigation items, tabs, image catalogs) is written `nameof(ShellText.Nav_Menus)` so the compiler checks it; a key built at run time (`$"Role_{role}"`, `$"Theme_{key}"`, the FAQ pairs) gets a check in `ResourceCompletenessTests`.
- **Placeholders** `{0}`, `{1}` (formatted with the current culture); **plurals** are explicit pairs `Key_One` / `Key_Other` used through `T.Plural(count, "Key", args…)` (`LocalizerExtensions`; `{0}` = the count) — the suffixes `_One`/`_Other` are reserved for that. **No sentence fragments**: one key per sentence; a link inside a sentence becomes a sentence plus a link text; a highlighted part of a headline is marked with `[…]` inside the one string (`LandingPage.Highlight`). A no-break space (U+00A0) inside a value keeps words together. Values are one line (the working copies are CRLF).
- **Validation**: `[Required(ErrorMessageResourceType = typeof(AccountText), ErrorMessageResourceName = nameof(AccountText.Valid_EmailRequired))]` — full sentences for app-only input models (the account pages, the invite form with `TeamText`), `SpeiseDirekt.ModelText` full sentences for the Model's entities (shared with the API, whose culture stays the server's, i.e. English; the English texts keep their wording, e.g. "The Name field is required."), `SpeiseDirekt.ValidationText` for generic `{0}` messages. `InputNumber`'s parse message: `ParsingErrorMessage` with `ValidationText.Number`.
- **Status messages** of the account pages: `StatusMessage` takes `IsError`; after a redirect `IdentityRedirectManager.RedirectToWithStatus(…, isError)` stores the flag in the status cookie (the old "starts with Error" rule only for old cookies).
- **Confirmations**: `INotificationService.ShowConfirmation(new ConfirmationRequest(T["…Title"], T["…Message", name]) { ConfirmText = T["…"], Destructive = true })` — the only form; the dialog adds only "Cancel"/"Abbrechen".
- **Scripts** never hard-code UI text: C# passes it (interop arguments, `data-*` attributes, the live region `#sd-announcer` filled by `SortableList` in C#). `shell.js` and `sortable-list.js` have no texts of their own. **FullCalendar** (`Shared/Calendar/FullCalendar`): `locale` = the page's language (only the English locale data is vendored; month and day names come from Intl), every text from `ShellText.Calendar_*` (buttons, prev/next/today/view hints, "+2 weitere", the list view's column hints, the empty text; "ganztägig" is set but not shown, the calendar hides event times), Monday first in both languages. **Chart.js** (`js/analytics.js`): `renderAnalyticsCharts(…, texts)` gets titles, axis titles, series and the tooltip count from `AnalyticsPage.ChartTexts()`; ticks and tooltip dates through `Intl.DateTimeFormat(lang)`, numbers through Chart.js' `locale`.
- **Formats**: user-visible values through `Localization/UiFormat` — `Price` "5,90 €" (de, no-break space) / "€5.90" (en), always euros; `Number`, `Date`, `LongDate`, `Time`. **Machine values stay invariant**: HTML attributes, CSS (`style="width: 12.5%"`), `data-*`, JSON, URLs, postMessage, change fingerprints, chart and calendar data use `CultureInfo.InvariantCulture` (`ToString(…, InvariantCulture)`, ISO dates; `System.Text.Json` is invariant). `LocalizationTests.GermanPages_WriteMachineValues_Invariant` scans every back-office page in German for a decimal comma in them. **Euro inputs** use `Shared/PriceInput` (text, `inputmode="decimal"`, shows "5,90"/"5.90", reads "5,90", "5.90", "1.234,50", "€ 5,90"; no sign) instead of `type="number"`, which a browser localizes by its own UI language (a German page in an English Chrome read "5,90" as 590); `Shared/InputTime` crosses "HH:mm" invariantly.

### SpeiseDirekt.Api (Web API)
- Controllers in `Controllers/`, routes under `/api/...`:
  - `MenusController`: menus come back with `translationGroupId` (read-only: `MenuDto` has no such field); `GET {id}/language-versions` lists the group (`MenuLanguageVersionDto`: id, name, language, `isCurrent`; just the menu when unlinked; 404 unknown); `PUT` refuses (400) a language another version of the group has; `DELETE` leaves the group (a single version left is unlinked).
  - `MenusController`, `CategoriesController`, `MenuItemsController`: CRUD via repositories (`MenuItemDto` has optional labels `IsVegan`/`IsVegetarian`/`IsSpicy`/`IsHalal`/`IsAlcoholFree`/`IsNew`/`IsPopular`, default false, and an optional `PriceOptions` list (`Kind`, `Name`, `Price`, `SortOrder?`): create sets them, update replaces them, omitted (null) keeps them, `[]` removes them; with variants `Price` is set to the lowest variant price. Items come back with their `priceOptions` in display order. `CategoryDto` has an optional `Description` (on update omitted keeps it, `""` removes it). `CategoryDto` and `MenuItemDto` take an optional `SortOrder`: create without it appends at the end, update keeps the value; lists come back in display order)
  - `RestaurantProfileController` (`/api/restaurant-profile`): `GET` (`CanViewMenus`, 404 without a profile) and `PUT` (`CanEditMenus`, 201 when created, 200 when updated; `RestaurantProfileDto` with the entity's validation; `LogoImagePath`/`CoverImagePath` must be `image/{id}` of an uploaded image, null keeps, `""` removes)
  - `AllergensController`: CRUD, scoped to a menu (`GET` requires `?menuId=`; `Code` must be unique per menu)
  - `QrCodesController`: CRUD plus `POST/DELETE {id}/timetable-entries` and `{id}/calendar-entries`
  - `UsersController`: the team, the owner's only (`Users*` policies: a manager gets 403). `POST` creates an Identity user + `TenantUser` as a manager (`CreateTenantUserDto(Email, DisplayName, Password?)`, enforces `MaxUsers`), `PUT` sets `IsActive` and an optional `DisplayName` (≤ 100, not empty; null = unchanged), `DELETE` deactivates (keeps the row; the back office's "Remove" deletes). A `role` or `customPermissions` sent by an older client is ignored (System.Text.Json skips unknown properties); `TenantUser.Permissions` is not in the JSON (`[JsonIgnore]`).
  - `AnalyticsController`: `traffic-per-user`, `traffic-per-menu`, `traffic-per-menuitem`
  - `ImageUploadController` (`/api/images`): upload (max 5 MB, resized to 600px), delete; `GET /api/images/{id}` is anonymous
  - `MenuCombosController`: CRUD via `IMenuComboRepository`, scoped to a menu (`GET` requires `?menuId=`). Validates: trigger item required, at least one included item, `ComboPrice >= 0`, trigger and included items must belong to the combo's menu (via `Category.MenuId`). On `PUT` the combo keeps its menu (`MenuId` in the DTO is ignored).
  - `MenuDisplayController` (`/api/public`, anonymous): menu for a QR code (records a view; items include their price options), the menu's combos (`GET menu/{menuId}/combos`, returns `PublicMenuComboDto` with trigger item, included items and price), the restaurant profile of the menu's owner (`GET menu/{menuId}/restaurant`, `PublicRestaurantProfileDto` without ids, images as `/api/images/{id}`, 404 without one) and item click tracking
- Request models in `Dtos/`. Responses currently return entities directly; JSON uses `ReferenceHandler.IgnoreCycles`.
- CORS policy `AllowAll`. `public partial class Program` exists so the tests can use `WebApplicationFactory<Program>`.

### SpeiseDirekt.Api.IntegrationTests
- `CustomWebApplicationFactory`: replaces SQL Server with SQLite in-memory, swaps `IUserIdProvider` for a fixed `TestUserId`, and adds the `TestScheme` auth handler (`TestAuthHandler`), which authenticates every request as that user (the tenant owner, so all permissions apply).
